03 화환 배송 관리 시스템

2-1. 사용 목적

전략구매팀으로 접수되는 화환과 상조용품 배송 요청을 등록하고, 배송 진행 상태와 변경 이력을 관리하기 위한 시스템입니다. 일반 화환 배송뿐만 아니라 장례식장 배송에 사용하는 BS 양식을 별도로 지원합니다.

2-2. 주요 기능

  • 화환 배송 요청 신규 등록 / 수정 / 삭제
  • 배송 상태 변경
  • 일반 양식과 BS 양식 구분
  • 등록일·배송일·금액·상태 기준 정렬, 상태별·조건별 필터링
  • 카카오톡 배송 요청 내용 공유
  • 엑셀 파일 업로드 / 다운로드
  • 현재 현황 서버 저장, 사용자별 변경 이력 기록
  • 다른 사용자의 선행 저장 여부 확인
  • PC 및 모바일 화면 지원

2-3. 주요 등록 항목

일반 화환 등록 시 요청일/배송일, 요청자, 수령인, 배송지, 관계, 품목, 수량, 단가 또는 금액, 배송 상태, 관리 메모 등을 입력합니다. 실제 화면의 입력 항목은 현재 배포된 코드의 등록 양식을 기준으로 확인합니다.

2-4. BS 양식 (장례식장 배송)

주요 입력 항목: 빈소, 받는 분, 고인명, 수량. BS 양식으로 등록하면 데이터에 formType: "bs" 값이 저장되고, 목록에서는 BS 표시로 일반 배송과 구분됩니다.

확인 필요고인명, 빈소, 받는 분 정보가 엑셀 다운로드 및 재업로드 과정에서도 유지되는지 확인해야 합니다.

2-5. 배송 상태

pending 배송 준비
processing 배송중
completed 배송요청 완료
issue 확인필요
cancelled 배송완료
주의화면의 한글 상태명과 내부 코드값이 다릅니다. 코드를 수정할 때는 반드시 내부 코드값을 기준으로 확인하세요. 특히 completed는 "배송이 끝났다"는 뜻이 아니라 "배송 요청이 완료되었다"는 의미로 사용됩니다.

2-6. 카카오톡 공유

배송지, 수령인, 관계, 품목, 수량 등 배송에 필요한 정보가 공유 내용에 포함됩니다. 수정 시 확인할 사항:

  • 공유 문구가 정상적으로 만들어지는지
  • 일반 양식과 BS 양식이 각각 정상 표시되는지
  • 모바일과 PC에서 공유 링크가 정상 작동하는지
  • 외부 연결 주소가 올바른지

2-7. 서버 저장 구조

GitHub 연결 Vercel 프로젝트 + Vercel Blob Storage 사용.

deliveries.json → 화환 배송 목록 logs.json → 변경 이력 API: /api/deliveries /api/logs

화면에서 입력한 데이터는 브라우저에만 저장되는 것이 아니므로, 실제 운영 데이터는 반드시 서버 저장까지 완료해야 합니다.

2-8. 저장 버전과 충돌 감지

두 사용자가 같은 데이터를 동시에 열어 둔 상태에서 서로 다른 내용을 저장하면 기존 작업을 덮어쓸 수 있어, 서버와 화면의 saveVersion을 비교해 충돌을 감지합니다.

  1. 크롬에서 데이터를 수정하고 저장
  2. 엣지는 저장 전의 이전 데이터를 열고 있음
  3. 엣지에서 그대로 저장을 시도
  4. 서버 버전과 엣지 화면의 기준 버전이 다르면 충돌 경고
  5. 최신 서버 데이터를 다시 불러온 후 내용을 확인
주의충돌 경고가 나타났는데 강제로 저장하거나 코드를 우회하면 다른 사용자의 작업을 덮어쓸 수 있습니다.

2-9. 변경 이력

신규 등록·수정·삭제·상태 변경 작업은 변경 이력에 기록되며, 최대 10개까지 유지되고 화면에서 페이지 단위로 확인할 수 있습니다. 인수인계 전 테스트 등록·저장 이력은 삭제하거나 실제 데이터와 구분되도록 정리합니다.

2-10. 운영 순서

  1. 로그인 후 서버 데이터를 새로 불러온다
  2. 기존 배송 목록과 마지막 저장 시각을 확인한다
  3. 신규 배송 요청을 등록한다
  4. 입력 내용과 배송 상태를 확인한다
  5. 필요한 경우 카카오톡으로 배송 내용을 공유한다
  6. 현황 저장을 눌러 서버에 저장한다
  7. 저장 완료 시각과 변경 이력을 확인한다
  8. 필요하면 엑셀 파일을 다운로드한다
  9. 새로고침 후 저장 내용이 유지되는지 확인한다

2-11. 주의사항

  • 화면에서 수정한 뒤 반드시 현황 저장을 해야 한다
  • 엑셀 업로드 전 기존 데이터를 다운로드해 백업한다
  • 다른 사용자가 작업 중인 경우 저장 충돌 여부를 확인한다
  • BS 양식은 일반 화환 양식과 입력 구조가 다르다
  • 테스트 데이터는 실제 운영 데이터와 섞이지 않게 한다
  • 서버 새로고침은 최신 데이터를 다시 불러오는 작업이므로 저장하지 않은 화면 내용이 사라질 수 있다
  • 코드 수정 후에는 일반 등록, BS 등록, 카카오 공유, 저장, 재접속까지 모두 테스트한다

04 FITI시험연구원 구매현황

3-1. 정확한 사용 목적

품목 마스터 관리 프로그램이 아님전략구매팀의 구매·발주실적 엑셀 파일을 불러와 연도, 부서, 품목, 계약구분별 구매금액과 수량을 분석하기 위한 구매현황 분석용 화면입니다. 소모품 품목명 정의 업무와는 별개의 업무로 구분해야 합니다.

3-2. 업로드 가능한 파일

CSVXLSXXLS

엑셀 파일은 첫 번째 시트를 기준으로 읽습니다. CSV는 기본적으로 UTF-8로 읽으며, 정상적으로 읽히지 않는 경우 EUC-KR 방식으로 다시 처리합니다.

3-3. 필요한 엑셀 컬럼

필수있으면 함께 반영
발주일
품목명		 요청부서/부서 · 품목코드 · 발주수량 · 발주금액 · 발주단가 · 분류/품목구분 · 계약구분 · 구매업무 · 구매유형 · 계약방법

발주일이나 품목명이 없는 행은 정상 데이터로 등록되지 않습니다.

3-4. 파일 추가와 교체

기존 데이터가 있는 상태에서 새 파일을 업로드하면 추가 또는 교체 중 선택합니다. 추가 업로드 시 중복 판단 기준:

발주일 + 품목코드 + 발주수량 + 발주금액
한계같은 날짜에 동일 품목을 같은 수량·금액으로 여러 번 발주한 경우, 서로 다른 발주인데도 중복으로 제외될 수 있습니다. 업로드 후 기존/신규/최종 건수와 원본과 앱의 금액 합계를 반드시 대조하세요.

3-5. 품목 자동 분류

분류/품목구분 컬럼이 있으면 우선 사용하고, 없으면 품목명 단어 기준으로 자동 분류합니다 (시약 · 인쇄물 · 공기구비품 · 수리 · 교정 · 시험소모품). 예: Standard, Solution, Reagent, HPLC, Acid, CRM, 시약 등의 표현이 있으면 시약으로 분류될 수 있습니다. 이는 보조 기능이므로 실제 분류와 다를 수 있습니다.

3-6. 계약구분 자동 판정

사용 컬럼: 구매업무 · 계약구분 · 구매유형 · 계약유형 · 입찰구분 · 입찰방법 · 구분 · 계약방법 · 구매구분

주요 계약구분: 수의계약 · 나라장터 입찰 · 입찰-소모품 · 입찰-사업비 · 입찰-일반구매요청 · 사업비. 나라장터/조달청/G2B 문구가 있으면 나라장터 입찰로 우선 분류합니다.

임시 분류 기준 (법적 확정 기준 아님)2천만 원 이상 → 나라장터 입찰 / 2천만 원 미만 → 수의계약. 자동 분류된 계약구분은 원본 자료와 반드시 비교해야 합니다.

3-7. 데이터 품질 검사

업로드 후 자동 점검 항목: 발주일 없음/비정상 연도, 발주금액 0원, 발주수량 0, 품목코드 없음, 계약구분 미분류, 신규 처리 건수, 최종 전체 건수. 품목코드가 없는 데이터는 전체 구매금액에는 포함되지만 연도별 단가 이력 계산에는 제한이 생깁니다.

3-8. 검색 및 필터

3-16. 데이터 저장 방식

서버 저장 + 브라우저 저장업로드 데이터, 전사/부서별 예산, KPI 스냅샷, 업로드 파일 정보는 현재 PC · 현재 브라우저의 localStorage에 저장되고, 동시에 Vercel Blob(/api/state)에도 저장되어 다른 PC에서도 같은 데이터를 볼 수 있습니다.
Blob 연결이 먼저Vercel 프로젝트에 Blob Storage를 연결하고 다시 배포(Redeploy)해야 서버 저장이 동작합니다. 연결 전에는 /api/state 호출이 실패하고 브라우저 저장만으로 동작합니다.
  • 서버 저장이 동작하면 다른 PC·브라우저에서도 같은 데이터가 보인다
  • 서버 저장 전에는 같은 PC와 같은 브라우저에서만 데이터가 유지된다
  • 브라우저 사이트 데이터를 삭제하면 로컬 저장 데이터가 사라질 수 있다
  • 시크릿 모드에서는 데이터가 유지되지 않을 수 있다
  • 데이터가 지나치게 많으면 저장 용량을 초과할 수 있다
  • 저장 실패 경고 시 원본 파일을 다시 업로드해야 할 수 있다
  • 중요 자료는 반드시 원본 엑셀로 별도 보관한다

저장된 구매 데이터가 없으면 코드에 포함된 샘플 데이터가 표시될 수 있으므로 실제 구매실적으로 오인하지 않도록 주의합니다.

3-17. 삭제 버튼

상단 삭제 버튼은 dashboard_db(구매 데이터)만 삭제합니다. 전사 예산·부서별 예산·KPI 스냅샷·업로드 정보는 각 기능의 초기화/삭제 버튼으로 별도 삭제해야 합니다.

3-18. 운영 순서

  1. 최신 구매실적 엑셀 파일을 준비한다
  2. 원본 파일을 별도 폴더에 백업한다
  3. FITI시험연구원 구매현황에서 업로드 버튼을 누른다
  4. 기존 데이터에 추가할지 전체 교체할지 선택한다
  5. 업로드 완료 후 전체/신규 처리 건수를 확인한다
  6. 날짜 오류·금액 0원·품목코드 없음 등 품질 검사 결과를 확인한다
  7. 연도·부서·분류·계약구분 필터가 정상 생성되었는지 확인한다
  8. FITI시험연구원 구매현황의 총 발주금액과 원본 엑셀 합계를 비교한다
  9. 자동 분류된 계약구분·품목 분류를 표본 확인한다
  10. 필요 시 전사/부서별 예산을 입력한다
  11. 분석 결과 확인 후 필요한 필터 결과를 엑셀로 저장한다
  12. 중요한 시점에는 KPI 스냅샷을 저장한다

05 비거주지 근무직원 사택 임차현황

4-1. 사용 목적

회사에서 운영하는 사택의 임차계약 정보를 관리하고 계약 종료 예정 사택을 미리 확인하기 위한 현황 화면입니다. 지역별 사택 현황과 계약 기간, 보증금, 월세, 임차인, 담당자 등을 관리합니다.

4-2. 주요 기능

  • 사택 임차계약 엑셀 업로드, 전체 목록 조회
  • 신규 등록 / 수정 / 삭제
  • 지역별 필터, 임차인·주소·담당자 검색
  • 지역별 사택 수 통계
  • 최초계약일 기준 정렬
  • 계약 종료 3개월 이내 항목 표시
  • 엑셀 다운로드, 서버 현황 저장, 변경 이력 기록
  • 필터 영역 접기·펼치기, 저장 버전 확인

4-3. 주요 관리 항목

항목의미
계약 시작일현재 계약이 시작된 날짜
계약 종료일현재 계약서상의 종료 날짜
최초계약일해당 사택의 최초 계약이 시작된 날짜

지역, 주소, 임차인, 보증금, 월세, 담당자, 비고 항목도 함께 관리합니다.

주의계약 시작일 · 계약 종료일 · 최초계약일은 서로 의미가 다르므로 혼동하지 않아야 합니다.

4-4. 정렬 및 검색

기본 정렬은 최신 등록순이며, 최초계약일 기준 정렬도 가능합니다. 지역·주소·임차인·담당자 조건으로 검색·필터링할 수 있고, 필터 영역은 접기·펼치기가 가능합니다(초기 화면은 닫힌 상태일 수 있음).

4-5. 계약 만료 3개월 표시

오늘 날짜를 기준으로 앞으로 3개월 이내 계약이 종료되는 사택을 만료 예정으로 표시합니다. 판정 기준: 다음 계약 종료 예정일이 오늘과 같거나 이후이고, 오늘부터 3개월 이내일 것.

계약 종료일에 저장된 연도가 현재 연도와 맞지 않으면 월/일을 기준으로 올해 또는 다음 해의 종료 예정일을 계산합니다. 예: 기준일이 7월 16일이면 10월 16일까지 종료 예정인 계약이 포함되고, 연말에는 다음 해 1~2월 종료 계약도 정상적으로 포함되어야 합니다.

만료 예정이 이상하게 표시될 때 확인할 것계약 종료일의 실제 연도 · 월과 일 · 현재 날짜 · 날짜 형식 · 엑셀에서 날짜가 문자열로 저장되어 있는지

4-6. 지역별 통계

지역별 사택 수를 통계로 확인할 수 있으며, 통계에서는 기타 지역을 제외하도록 설정되어 있습니다. 따라서 전체 목록 건수와 지역 통계 합계가 다를 수 있으나, 기타 데이터가 삭제된 것이 아니라 통계 계산에서만 제외된 것입니다.

4-7. 서버 저장 구조

Vercel 서버 + Private Vercel Blob Storage 사용.

Blob 경로: cphg-dashboard/data.json 저장 데이터: - 사택 계약 데이터 - 변경 이력 - 업로드 원본 파일명 / 소스 파일 정보 - 서버 마지막 저장 시각 / 마지막 저장 사용자 - 저장 버전

서버 API에서는 데이터 배열이 정상적으로 전달되지 않으면 저장하지 않고 오류를 반환하도록 방어 처리가 되어 있습니다.

4-8. 저장 방식

현황 저장 버튼 → 서버에 현재 데이터 저장 → 엑셀 파일 저장 여부 선택. 엑셀 다운로드를 취소해도 서버 저장이 먼저 정상 완료되었다면 서버 데이터는 유지됩니다. 저장 후 확인할 것: 저장 완료 메시지, 마지막 저장 시각/사용자/버전, 새로고침 후 데이터 유지 여부.

4-9. 운영 순서

  1. 비거주지 근무직원 사택 임차현황에 접속한다
  2. 서버의 최신 데이터를 불러온다
  3. 기존 사택 목록과 마지막 저장 시각을 확인한다
  4. 신규 등록 또는 기존 계약 정보를 수정한다
  5. 계약 종료일과 최초계약일을 다시 확인한다
  6. 만료 예정 3개월 목록에 정상 반영되는지 확인한다
  7. 현황 저장을 눌러 서버에 저장한다
  8. 필요한 경우 엑셀 파일을 다운로드한다
  9. 새로고침 후 데이터가 유지되는지 확인한다
  10. 변경 이력과 저장 시각을 확인한다

4-10. 주의사항

  • 엑셀 업로드 전 기존 서버 데이터를 백업한다
  • 빈 엑셀 파일이나 잘못 읽힌 파일을 서버에 저장하지 않는다
  • 계약 종료일과 최초계약일을 구분한다
  • 만료 예정 계산은 단순히 원본 연도만 비교하지 않는다
  • 기타 지역은 목록에는 있지만 통계에서 제외된다
  • 저장 후 반드시 새로고침하여 유지 여부를 확인한다
  • 현재 운영은 기본적으로 단일 사용자 사용을 전제로 한다
  • Blob Storage는 Private 설정을 유지한다
  • 서버 코드에서 캐시를 사용하면 새 데이터가 바로 표시되지 않을 수 있으므로 no-store 설정을 유지한다

06 ERP 소모품·시약 품목명 정의 업무

5-1. 사용 목적

기존 ERP에 등록된 불규칙한 품목명을 동일한 기준으로 정리하고, 신규 품목을 등록할 때 제조사와 제품 정보를 정확하게 식별할 수 있도록 표준 명칭을 작성하는 업무입니다. 품목명은 제조사 카탈로그, 제품 라벨, 성적서, 제품 페이지 등을 확인한 후 작성합니다.

원칙확인되지 않은 정보를 임의로 추정해서 입력하지 않습니다.

5-2. 공통 작성 원칙

  • 항목 구분자는 / 사용, 슬래시 앞뒤 공백 없음
  • 제조사명은 가능한 한 공식 영문 풀네임 사용
  • 제조사 품번은 원문 그대로 입력 (점·하이픈·영문자·숫자 임의 변경 금지)
  • 용매 표기는 제조사 표현 유지
  • 농도·순도·등급은 확인된 경우만 입력

11 핵심 요약

화환 배송 관리 시스템은 화환 배송 요청을 등록하고 서버에 저장하는 운영용 시스템입니다.

FITI시험연구원 구매현황은 구매실적 엑셀을 브라우저에 불러와 KPI, 예산, 품목, 부서, 계약구분별 통계를 확인하는 분석용 시스템이며 품목을 직접 수정하는 프로그램은 아닙니다.

비거주지 근무직원 사택 임차현황은 사택 계약정보를 서버에 저장하고 계약 종료 3개월 이내 항목을 관리하는 시스템입니다.

소모품 품목명 정의 업무는 제조사 공식 자료를 확인하여 ERP 품목명을 동일한 형식으로 표준화하는 별도의 데이터 정비 업무입니다.

4.2 실적을 어디서 보나

ERP 추출 엑셀에는 「단가계약」이라는 칸이 없습니다. 계약구분은 수의계약 · 입찰-소모품 · 입찰-사업비 · 입찰-일반구매요청 · 사업비 다섯뿐이라, 단가계약 건은 품목명으로 찾아냅니다.

3.2 사전규격공고
